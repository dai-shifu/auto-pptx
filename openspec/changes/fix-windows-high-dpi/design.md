## Context

`src/gui.py` 使用 Tk 创建主窗口和系统文件对话框。已检查的本地单文件 exe 未声明 DPI 感知。用户在 150% 下开启「应用程序」兼容性覆盖后，主窗口和文件对话框均恢复清晰；该对照未测量进程实际使用的 DPI 模式。

## Goals / Non-Goals

- 在主显示器采用固定缩放时，让发布 exe 无需兼容性覆盖即可清晰显示。
- 让预览行随实际字体高度留出上下间距，文字和勾选符号不贴边或裁切。
- 保留原生对话框、当前预览列宽策略、配置与生成行为。不做跨不同 DPI 显示器的动态适配。

## Decisions

1. 采用 Windows System DPI Awareness。锁定的 Nuitka 4.1.3 没有用于声明 DPI 感知的清单选项；不后处理 onefile 的 PE 资源。使用仅限 Windows 的启动初始化，在创建任何 Tk 窗口前调用 `SetProcessDPIAware`。使用实机查询确认 GUI 窗口的实际 DPI 感知模式，不只检查启动器清单。
2. 让 Tk 按实际 DPI 绘制字体。不硬编码 150% 或强制覆盖 `tk scaling`。为 Windows 数据预览设置独立的 Treeview 样式。行高取主题默认行高与「实际字体行高加上下内边距」的较大值，避免在低缩放下反而压缩行距。使用当前 DPI 换算内边距，不改变表头和列宽。
3. 在关闭兼容性覆盖的 Windows 桌面验证同一成品。以主显示器分别设为 100% 和 150% 的桌面会话为准；必要时重新登录以刷新系统 DPI。用合成输入打开两个浏览对话框、载入并勾选数据、触发长文本提示，并检查生成流程。Tk 缩放模拟和源码 GUI 测试不能代替这一步。

## Risks / Trade-offs

- 系统 DPI 感知不能保证窗口移到不同缩放的屏幕时仍清晰。本次不引入 Per-Monitor V2。
- 启用 DPI 感知后窗口物理大小可能与旧版不同。验收可读性与控件完整性，不要求恢复旧版位图放大后的尺寸。
- 若实际成品验收失败，保留试构建并修正后再发布。不修改配置格式，也不替用户改系统兼容性设置。
