## Why

项目已完成公开源码脱敏，但首次迁移、程序构建和日常发版尚未形成可重复的流程。用户确认后续直接在公开仓库开发，且主要面向国内用户，需要同时解决 Windows 程序获取和国内下载验收。

## What Changes

- 将内部仓库到公开仓库的源码快照导出限定为一次性迁移；迁移后公开仓库成为唯一开发主仓库，后续更新保留公开历史。
- 增加提交和 PR 的自动测试，以及版本标签触发的 Windows x64 发布构建；手动触发仅生成试构建产物。
- 统一项目版本与可执行文件版本来源，校验发布标签，只分发独立 Windows exe 和 SHA-256 校验附件；不附带配置或示例包，程序首次启动自行创建配置。
- 自动准备 GitHub Release 草稿，公开前验证下载包与国内分发渠道；各渠道复用同一份构建产物。
- 优先评估 Gitee 作为国内镜像和下载入口，保留可重试的人工上传步骤；渠道未实测通过时不得宣称已支持国内直接下载。
- 更新 README 与发布说明，区分首次迁移、日常开发、试构建、正式发版和失败重试。

## Capabilities

### New Capabilities

- `public-release-workflow`: 一次性公开迁移、自动测试、版本校验、Windows 构建、试构建与 Release 草稿。
- `domestic-release-distribution`: 国内下载入口、同一产物分发、下载验收和渠道失败重试。

### Modified Capabilities

无。沿用已有源码脱敏与合成 fixture 约束，不改变应用生成行为或用户配置格式。

## Impact

- 涉及新增 `.github/workflows/`、必要的迁移及打包辅助脚本、`build.py`、README、`docs/公开发布.md` 和必要测试。
- 版本以 `pyproject.toml` 为来源，依赖使用现有 `uv.lock`；不增加应用运行时依赖。
- 需要 GitHub 托管 Windows 构建环境；国内渠道选定、仓库地址与实际下载验证在发布部署时完成。
- 本地实现不创建远程仓库、不推送内部历史、不发布真实 Release、不上传第三方附件；外部操作在明确目标后单独执行。
