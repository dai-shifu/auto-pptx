## Context

仓库没有现存 CI 或发布 workflow。`build.py` 使用 Nuitka 单文件模式，Windows 版本在脚本中写死为 0.1.0，项目版本另在 `pyproject.toml` 声明。`docs/公开发布.md` 只覆盖已准备的源码快照和新仓库创建，缺少可重复导出入口及后续发版流程。GUI 测试在无显示环境时会跳过。

用户决定迁移后直接在公开仓库开发，以国内 Windows 用户为主要受众。已有脱敏变更约束继续适用于首次迁移，不修改或推送内部 Git 历史。

## Goals / Non-Goals

**Goals:**

- 一次性导出最终公开文件；以后仅维护公开仓库的一条开发主线。
- 提供完整测试、可追溯的 Windows x64 构建及一致的版本信息。
- 普通用户只需下载 exe 即可使用，无需安装 Python；配置由程序首次启动自行创建，使用说明保留在源码文档。
- 国内外渠道复用同一产物，国内下载通过实际验收后再正式公布版本。

**Non-Goals:**

- 不改变 Excel 到 PPT 的行为、GUI 或现有配置格式。
- 首版不增加 macOS/Linux 程序、安装器、自动更新、签名采购、付费下载服务或复杂发布平台。
- 不长期维护内部与公开仓库双向同步，不默认增加 Gitee 自动上传集成或凭据。

## Decisions

### 1. 一次性迁移与日常发布分离

增加使用 Python 标准库的轻量导出脚本，以经过检查的版本控制文件清单读取最终工作树内容，显式排除 Git 元数据、环境、缓存、工具本地设置和生成物；拒绝导出越界符号链接或缺失的候选文件。生成 `dist/public-release/` 下源码目录、源码 ZIP 和逐文件大小及 SHA-256 清单，避免复制整个目录。首次导出应包括本次完成的 workflow、脚本和文档；导出前完成已有公开内容验收。

迁移时在独立目录初始化新 Git 历史。之后源码直接在公开主仓库维护，普通更新保留公开仓库历史，不反复初始化仓库。快照导出不是日常发版的前置依赖；这样避免长期双仓库同步。

### 2. 分开维护 CI 与 Release workflow

`ci.yml` 面向提交和 PR，以 Python 3.12、锁定依赖和 Linux Xvfb 运行完整测试，验证显示环境实际可用，不能用 GUI 跳过来替代覆盖。

`release.yml` 支持版本标签和手动试构建。正式标签严格使用 `vX.Y.Z`，校验标签版本等于项目版本；格式或版本不符时在编译前失败。手动触发只上传构建产物，不创建 Release。两条路径都先通过测试，再在 Windows x64 环境安装锁定依赖并运行相同构建与打包入口。

固定 Python 和明确的 runner 版本，实施时核对可用 action 版本。构建任务使用读取权限，只有正式标签的草稿发布任务获得写 Release 所需权限；按标签串行处理重复发布。保留可下载构建产物，便于重试分发。

Windows job 的默认 shell 明确设为 Git Bash；用户要求不维护 PowerShell 脚本。打包、校验和、Windows 版本资源与真实 Tk 窗口启动检查统一由 Python 脚本实现，必要的 Windows API 通过标准库 ctypes 调用。Windows 本地复现说明同样使用 Git Bash。

### 3. 统一版本、发布包与构建证据

`pyproject.toml` 是唯一人工维护的版本来源。`build.py` 读取该版本，按 Nuitka 要求转换为 Windows 文件及产品版本；构建阶段核对锁定 Nuitka 的控制台和版本参数。保留现有单文件与 tkinter 模式，不引入另一套构建配置。

用户进一步确认只分发 exe，不提供 config.toml。将编译出的单文件复制为 `auto-pptx-vX.Y.Z-windows-x64.exe`，不生成用户 ZIP，不附配置或示例。配置沿用程序在 exe 同目录首次启动创建、成功生成后保存的既有行为；目录需要可写，不修改应用逻辑。源码继续保留许可证、培训文档与合成 fixtures，供维护者验证。

生成独立 `SHA256SUMS.txt`，对最终 exe 计算校验和，作为可选下载附件。`release-info.json` 记录版本、源码提交与 workflow run，仅保存在构建 artifact，不作为必需用户下载。试构建文件名标注运行标识。Python 检查脚本将 exe 复制到无配置的临时目录，检查版本资源、可见窗口和首次配置创建；最小生成由正式发布清单进行人工实机验证。

### 4. Release 草稿与国内分发复用同一产物

正式标签构建完成后自动创建或更新该标签的 GitHub Release 草稿，附 exe、SHA-256 和版本及提交信息。重试时已存在的正式 Release 必须保持不变；附件相同则跳过，草稿中同名附件内容不同时必须明确失败，不能静默覆盖。

维护者从构建产物或草稿取得文件，上传到选定的国内渠道。第一版采用文档化人工上传，避免在候选平台未验证时维护 API 与凭据。后续如需自动同步，应在渠道确定后另行设计。

Gitee 是优先验证的候选，尚未实测，不承诺附件限制、免登录下载或速度满足需求。首次上线核对最新官方限制与实际 exe 大小，使用国内网络和未登录浏览器测试文件下载、账号或客户端要求、完整性及程序运行。若不满足，则换渠道并重复验收；付费对象存储不在本次默认范围。

### 5. 下载入口与失败处理

README 首屏提供明确的 Windows 下载说明。真实地址配置前使用清楚的待配置状态，不放看似可用的占位链接；国内入口只有验收通过后才标记可用。Gitee 项目首页承载中文说明、源码镜像和国内附件入口；镜像只作为公开仓库的单向副本，贡献入口统一指向主仓库。

国内上传失败时保留 GitHub 草稿与原始附件，按原标签和 SHA-256 重试，不重新构建。两个渠道验证一致后，维护者手动将草稿转为正式发布并更新下载说明；该人工步骤负责最终下载验收，不增加审批系统。

## Risks / Trade-offs

- [国内候选渠道需要登录或无法容纳附件] → 发布前实测；未通过则保持待配置状态，另选渠道，不承诺已支持。
- [Windows 编译成功但程序无法启动或缺失资源] → 验证独立 exe 的启动、首次配置创建和最小生成流程，并记录自动或人工验证边界。
- [无显示环境导致 GUI 测试跳过] → CI 配置 Xvfb 并预检真实 Tk 窗口可创建。
- [免费渠道人工同步遗漏] → 发布清单核对版本、附件和 SHA-256，国内通过前保留草稿。
- [迁移快照陈旧或夹带机器文件] → 从最终文件清单导出并独立解压核验，重复执行既有公开内容验收。
- [依赖锁定不等于二进制逐字节可重现] → 记录提交、依赖与运行标识，各渠道分发同一文件，不要求跨构建哈希相同。

## Migration Plan

1. 在内部仓库完成 workflow、构建及导出入口和文档，运行本地可执行验证。
2. 重新生成并检查公开快照，独立解压验证；内部仓库历史保持完整。
3. 明确公开地址后初始化新仓库，从公开主仓库执行 CI 和手动试构建。
4. 配置国内候选项目，完成国内未登录下载和 Windows 包体验验收。
5. 首次版本标签构建草稿，按同一产物完成国内分发，再正式发布。

出错时保留原始构建与校验信息，修复源码后使用新版本标签；已公开的版本和附件不覆盖。国内分发失败只重试分发。

## Open Questions

- GitHub 主仓库与国内候选项目的实际地址：不阻塞本地实现，影响上线后的链接配置。
- Gitee 附件容量、免登录要求和国内网络表现：需用最终 Windows exe 实测，当前无验证结论。
- 首次托管 Windows 构建和打包程序验证结果：无法在当前 Linux 本地环境宣称已完成。
