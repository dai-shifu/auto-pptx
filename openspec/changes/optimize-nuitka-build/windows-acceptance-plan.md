# Windows 收尾方案

先修复源码 GUI 和测试环境，再验证最终 exe。构建、源码测试、成品生成和性能证据分别记录，全部满足后才能完成任务 4.3。

## 调研结论（2026-11-18）

| 问题 | 已有证据 | 结论与下一步 |
| --- | --- | --- |
| 可分发运行库缺失 | Nuitka 检测不到可分发运行库。原 `yes` 模式失败；改用 `auto` 后本机试包成功 | 记录缺库警告及产物包含情况，仍需干净 Windows 启动和生成验收 |
| 短文本提示框高度错误 | 当前 Windows Python 3.12.13、Tk 8.6.12 三次诊断均出现 Text 初始 1×1，被误算为 95 行；布局后实际 2 行，窗口仍高 400px | 已确认实现问题，先完成 `fix-windows-tooltip-layout` |
| 长文本滚动失败 | 原始 HEAD 日志有负滚动比例；本次布局稳定后能滚动到底，范围 `(0.9391, 1.0)` | 历史失败尚未稳定重现，不直接判定测试过时或问题已解决 |
| 真实指针跨窗失败 | 历史结果不稳定；测试按单元格坐标推定终点，没有根据最终提示框位置确定路径 | 复查真实行为，按实际窗口几何规划指针测试，保持进入可读和离开关闭要求 |
| Tk 初始化跳过 | 旧日志称 listbox.tcl 无法读取；当前文件存在，四轮独立诊断初始化成功 | 检查解释器、库路径、连续 root 创建与完整 suite 顺序；不能直接据旧日志要求重装 |
| 验收覆盖不足 | ci.yml 只跑 Linux suite；check_windows.py 只检查版本、启动、首次配置与退出清理 | 增加 Windows 源码回归，并补最终 exe 的真实生成验收 |

本机试包不代替 Windows CI 构建和干净机器验收。

## 1. 固定 Windows 验证环境

优先使用已有 `windows-2022` runner。使用 setup-python 提供的 Python 3.12 x64 及锁定依赖，记录解释器、Tk patchlevel、缩放、实际编译器和 Nuitka 版本。确认能创建真实窗口，再运行 GUI 测试；初始化失败与跳过不能作为 Windows 验收通过。

编译前记录 Nuitka 4.1.3 的运行库检测结果。CI 与本地 Windows 都使用 `auto`：找到则包含，找不到则警告并继续。不手工从 System32 复制 DLL，不强制切换编译器。正式 exe 仍交由 CI 构建。

本地 Tk 文件若确实缺失，先验证同一解释器和库路径，再修复或重建环境；不以修改环境变量掩盖路径混用。真实指针验收必须有交互桌面。

## 2. 完成 GUI 修复与测试更新

按 `fix-windows-tooltip-layout` 的 delta spec、design 和 tasks 实施。先保留失败复现，再修复实际 Text 宽度可用前计算高度的问题。

允许移除固定 400px、高度小于 200px、固定屏幕终点等不属于功能合同的假设，但必须保留紧凑高度、长文本完整可读、滚动到底、窗口复用、鼠标进入停留及离开关闭断言。等待布局使用有超时的状态检查。若功能仍不满足 spec，修代码；若仅测试依赖了旧假设，更新测试并说明与 delta spec 的对应关系。不得新增无条件 skip。

Windows 与 Linux 运行相关及完整 suite，Windows 额外重复相关 GUI 用例并人工复核默认和另一种缩放。仅在所需 GUI 测试实际执行并通过后进入成品验收。

## 3. 最终 Windows 构建与生成验收

使用当前 Nuitka 参数完成构建，保留日志、编译报告、运行库包含情况、最终文件大小和 SHA-256。检查收窄依赖后，Tk、图片与图表所需模块和数据仍完整。构建失败即停止打包。

先执行现有成品启动检查。再在独立可写目录，以仅交付 exe 的方式运行真实 GUI，输入使用 tests/create_fixtures.py 的合成构造器生成，并补 PNG 图片及含嵌入工作簿的图表。不得用源码入口生成代替 exe 生成。

验证首次配置、Excel 读取、选择行、文本及表格替换、预期页数、原始页移除、模板标识与未映射占位符保留及对应警告、图片字节、图表关系和值、嵌入工作簿与配置保存。结构检查可以在外部验证环境完成，目标运行环境不能借用项目源码或开发依赖。

同一 SHA-256 的 exe 还须在没有项目 Python、Build Tools 和开发依赖的干净 Windows 环境执行上述启动及生成验收，并记录已有 VC 运行库状态。构建 runner 中的临时目录隔离不能替代干净机器验收。

CI 尽量自动执行成品生成检查；人工环节必须保存结果及输出检查证据。Windows 源码测试 job 应成为发布构建的前置条件。实际验证一次缓存保存与后续 workflow 恢复、报告上传；每次运行保留对应 run 标识。

## 4. 冷热构建与完成条件

固定 Windows 机器、源码路径、Python、依赖和编译器。使用全新的绝对 NUITKA_CACHE_DIR，清理上一轮派生构建对象后做冷构建，再只保留专用缓存、清理派生对象做热构建。记录主程序与 onefile 引导程序的命中和 miss、总耗时及最终体积，不把残留对象直接复用算作 C 缓存命中。

至少取得最终配置的冷、热两轮数据。若要声明依赖裁剪带来的 Windows 加速或体积比例，还须在相同环境为原始整包配置补齐冷、热基线。无法补齐时只报告最终配置的两轮数据，不沿用 Linux 优化比例。

任务 4.3 的完成条件：Windows 源码 suite 及所需真实 GUI 检查通过；记录运行库包含情况；最终 exe 启动、生成及干净机器验收通过；冷/热数据、报告和远程缓存证据齐全。任何一项缺失继续标记待验收。

## 范围

本轮先关闭现有验收缺口。单文件解包缓存、LTO、PGO、压缩策略或编译器切换均不加入本次收尾；如有后续需求，在完整基线上单独评估。
