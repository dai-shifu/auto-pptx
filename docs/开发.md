# 开发与构建

环境准备、运行、测试和 PR 要求见[贡献指南](../CONTRIBUTING.md)。本页说明模块、示例维护和打包。

## 模块与生成流程

入口为 `run.py` → `src/gui.py`。主要模块位于 `src/`：

| 模块 | 职责 |
| --- | --- |
| `gui.py` | 文件、工作表、标题行、映射和数据选择 |
| `gui_layout.py`、`gui_tooltip.py` | 界面布局与悬停提示 |
| `excel_reader.py` | 读取工作表 |
| `auto_detect.py` | 建议标题行、模板列和映射 |
| `template_matching.py` | 按 `{{tpl::name}}` 索引模板页 |
| `generator.py` | 按选定的 Excel 行生成页面 |
| `pptx_engine.py` | 克隆页面、替换占位符、移除原始页 |
| `config.py` | 读写配置 |

映射方向为 Excel 列 → PPT 占位符。保存的配置和手动选择优先于自动建议。一行可用半角 `/` 引用多个模板页。生成后只保留新页面，保留模板标识和未映射占位符，供排查问题。用户规则见[使用指南](使用培训.md)。

排查生成问题时，先用一行合成数据复现，再对照 `tests/test_generator.py` 和 `tests/test_integration.py`。GUI 状态、布局和提示测试见 `tests/test_gui_*.py`。

`openspec/` 保存现行规格、变更设计和历史归档。修改行为前，先核对现行规格与活动变更。

## 维护示例与测试资源

重建日报模板、Excel 和成品：

```bash
uv run python -m scripts.build_bio_daily
```

此命令覆盖 `examples/bio-daily/` 中的三个文件，不更新预览。请从新成品导出预览，步骤见[示例说明](../examples/bio-daily/README.md)。

软件界面截图单独保存在 `docs/images/app-interface.png`，由中英文 README、使用指南和日报示例说明共用。界面变化后，加载合成日报示例重新截图，并同步核对各文档中的控件名称、设置和勾选状态说明。

README 的生成示意图为 `docs/images/generation-overview.svg` 和 `generation-overview.en.svg`，右侧均内嵌成品预览 `examples/bio-daily/previews/slide-02.png`。更新该预览时，同步替换两张示意图中的内嵌图片，并核对中英文说明、输入行数和输出页数。

测试资源位于 `tests/fixtures/`。仅在资源格式变更时运行 `uv run python tests/create_fixtures.py`，并同步测试。测试输出写入临时目录。

## 跨平台源码开发与测试

macOS、Linux 和 Windows 均直接运行源码。按[贡献指南](../CONTRIBUTING.md)准备 Python 3.11+、uv 和 tkinter，再在项目根目录运行：

```bash
uv sync --locked --group dev
uv run run.py
uv run --group dev pytest
```

源码开发和测试无需 Visual Studio、Build Tools 或 Windows 打包工具链。macOS 和 Windows 的 GUI 测试需可用的桌面及 Tk；Linux 无桌面环境时使用贡献指南中的 Xvfb 命令。

CI 使用 Python 3.12，在 Linux Xvfb 和 Windows 桌面分别运行完整源码测试。使用 `--require-gui` 时，Tk 初始化失败会报错，不会跳过。Windows 使用 Python 层输出捕获，避免文件描述符捕获干扰本机 Tcl 文件读取：

```bash
uv run --group dev python -m scripts.check_display
uv run --group dev pytest --require-gui --capture=sys
```

## 构建 Windows 程序

Windows exe 统一由 `.github/workflows/release.yml` 在 `windows-2022` 构建机上生成，使用 Python 3.12 x64。开发者在各自平台完成源码修改和测试后，使用现有 Windows 发布流程取得 exe；macOS 和 Linux 本地不承担 Windows exe 构建。

以下是 Windows CI 执行的依赖同步、构建环境检查和编译命令：

```bash
uv sync --locked --group build --python 3.12
uv run --group build python -m scripts.check_windows_build
uv run --group build build.py
```

Windows 构建显式要求 Nuitka 包含运行库。Windows CI 构建机的 Visual Studio 或 Build Tools C++ 组件提供 `VC/Redist/MSVC` 下的可分发文件。这是 CI 构建机依赖，不是源码开发要求。若 CI 提示找不到 Windows Runtime DLLs，应检查构建机组件；仅安装目标机器使用的 VC++ Redistributable 不能替代这些文件。脚本不强制切换编译器。

构建完成后输出耗时和最终单文件字节数，并保存 `dist/compilation-report.xml`。报告记录模块、DLL、数据文件及包含原因。第三方依赖由 Nuitka 自动分析，沿用自带配置处理图片插件；保留 Tk 资源和单文件压缩。新增动态导入时先检查报告，再定点补充必要模块。

Windows CI 恢复和保存 `NUITKA_CACHE_DIR` 指定的缓存，按系统、架构、Python 版本和锁文件隔离。每次运行使用新 key，并从相同依赖的前缀恢复。首次构建或缓存失效时会重新编译。编译报告单独上传为 `nuitka-report-*` artifact；编译失败后如有报告也会保留。报告不进入用户发布附件。

比较构建性能时，在 Windows 构建环境中固定机器、源码、Python、依赖及编译器。将 `NUITKA_CACHE_DIR` 指向一个此前不存在的绝对目录，运行一次构建，再使用同目录重复运行，分别记录冷、热构建耗时、缓存命中数、最终单文件大小和报告。比较依赖裁剪前后时，两组均需冷、热数据。

公开 Release 草稿前，在未安装项目 Python、Build Tools 或开发依赖的干净 Windows 环境验收草稿中的 exe。先在目标机器核对 exe 的 SHA-256 与 `SHA256SUMS.txt` 一致，再从独立可写目录运行。构建机启动通过或手动试构建成功，都不能替代正式包的生成验收。

在验证环境准备合成输入及 exe 副本；目标目录必须为空：

```bash
uv run python -m scripts.check_windows_generation prepare /path/to/empty-check-dir dist/auto-pptx.exe
```

在 Windows 运行副本，选择目录中的 `template.pptx` 和 `test_data.xlsx`，使用 Sheet `数据`、标题行 1、模板列 `模板`，全选并生成。确认出现 `acceptance_unmapped` 未替换警告。将目标环境的输出及保存的 `config.toml` 带回验证环境，运行：

```bash
uv run python -m scripts.check_windows_generation verify /path/to/check-dir /path/to/output.pptx
```

检查覆盖文本、表格、图片字节、图表数值、嵌入工作簿及内部关系。记录构建 run ID、exe SHA-256、首次启动、可见警告、Windows 与运行库状态及检查结果。验收失败时保留草稿，不公开。此工具的源码测试只验证检查器本身，不代表最终 exe 已通过。干净目标机器只需 exe 和合成输入，检查工具在外部验证环境运行。

发布辅助脚本位于 `scripts/`，产物写入 `dist/`。用户下载单个 exe，可选下载 `SHA256SUMS.txt`。程序首次启动时创建配置。

Windows 发布检查将 exe 复制到独立临时目录，验证版本、可见窗口和首次配置后，终止并等待启动进程及 GUI 子进程退出。CI 通过 `--runner-temp "$RUNNER_TEMP"` 指定 runner 临时目录；仅在验证和进程退出检查通过后，将文件占用导致的清理失败记录为警告，残留文件交给 runner 清理。本地默认仍将清理失败视为错误。

在 `pyproject.toml` 维护版本。正式标签为 `vX.Y.Z`，须与项目版本一致。版本标签触发测试、Windows x64 构建和 Release 草稿；手动触发只生成试构建产物。
